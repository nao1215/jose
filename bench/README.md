# Benchmarks

jose is measured the way a user runs it, one process per call from start to exit, with [himorime](https://github.com/nao1215/himorime). himorime builds jose (with `GOEXPERIMENT=jsonv2`, as the Makefile does), runs each command in interleaved rounds, and reports latency, CPU time, peak RSS and, for the large payloads, throughput.

```console
$ go install github.com/nao1215/himorime@latest
$ make bench            # himorime run bench
$ make bench-compare    # himorime compare --against main bench
```

## Regression suite: himorime.yaml

`make bench-compare` checks main out into a temporary Git worktree, builds it and your working tree, and measures both in the same rounds, so a background job slows both revisions instead of one. `BASE=v0.3.2 make bench-compare` compares against another revision. `himorime run --filter 'jws verify 10mb' bench` measures one benchmark, and `himorime run --tag smoke bench` only the small ones.

On a pull request, `.github/workflows/bench.yml` runs `himorime ci bench` the same way, with the base of the pull request as the base, on one runner. The job fails when a command is slower, uses more CPU time or more memory than the base beyond the tolerance in `himorime.yaml` with 95% confidence. A difference too close to call is reported as inconclusive and does not fail the job. The comparison is on the job summary page and the JSON report is kept as an artifact.

jose works on one message per call, so the size in a benchmark name is the size of the payload. Payloads are generated by `gen.sh` before measuring, so no fixture is added, and both revisions run the working tree's `gen.sh`. The keys (EC P-256, RSA 2048, OKP Ed25519, oct 256) and the tokens to verify or decrypt are written in setup by the jose of the revision measured, so no private key is committed; the cost of a key depends on its type and size only.

| Benchmark | Commands | Measures |
|-----------|----------|----------|
| `version` | `jose version` | starting jose |
| `jwk generate` | `--type` EC, OKP, oct, RSA | generating one private key of each type (RSA searches for primes, so it varies most) |
| `jws sign 1kb` | ES256, RS256, EdDSA, HS256 | signing a small payload, where start-up and reading the key dominate |
| `jws sign 10mb` | ES256, RS256, EdDSA, HS256 | hashing and encoding a 10 MiB payload |
| `jws verify 1kb` | ES256, RS256, EdDSA, HS256 | verifying a small JWS and printing the payload |
| `jws verify 10mb` | ES256, RS256, EdDSA, HS256 | decoding and hashing a JWS of a 10 MiB payload |
| `jws verify error` | an EC key other than the signer's | the failing verification, exit 1 |
| `jws parse 10mb` | `jws parse --all` | parsing a large JWS without verifying it |
| `jwe encrypt 1kb` | ECDH-ES, RSA-OAEP-256, A256KW, ECDH-ES with `--compress` | wrapping the content key each way and encrypting a small payload with A256GCM |
| `jwe encrypt 10mb` | the same four | encrypting (and deflating) a 10 MiB payload |
| `jwe decrypt 1kb` | the same four | decrypting a small JWE, the key encryption read from its header |
| `jwe decrypt 10mb` | the same four | decrypting (and inflating) a JWE of a 10 MiB payload |
| `jwe decrypt error` | an EC key other than the recipient's | the failing decryption, exit 1 |

`jose man` and `jose bug-report` are not measured: the first writes under /usr/share/man and the second opens a browser.

Numbers from different machines are not comparable; compare revisions on one machine, as `make bench-compare` and CI do.
